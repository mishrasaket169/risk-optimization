LIQUIDITY RISK OPTIMIZER
30 Implementation Prompts for Antigravity, Google Colab and Antigravity
A staged prompt pack for three Java 25 / JavaFX / PostgreSQL desktop applications, two XGBoost models, STOMP messaging, synthetic bank datasets, a simulated Indian-market exchange, integration, testing and Windows/Fedora deployment.
How to use this document
Run the prompts in order. Prompts 1–8 are for Antigravity and cover frontend-only work for all three desktop applications.
Run prompts 9–10 in Google Colab to train Model 1 (equity momentum) and Model 2 (liquidity/execution outcomes). Save model artifacts, feature schemas, evaluation metrics and model cards.
Run prompts 11–30 in Antigravity for Java backend, PostgreSQL, STOMP, integration, testing and deployment.
Give the complete prompt to the named tool. Do not ask it to implement every phase at once. Require it to inspect the repository, run tests and report what it actually verified.
If code already exists, preserve working modules and adapt the prompt to the current repository rather than regenerating the project.
Prompt allocation
Antigravity: 8 prompts | Google Colab: 2 prompts | Antigravity: 20 prompts | Total: 30 prompts.
Each prompt repeats a substantial shared project specification so it can be copied and used independently. Prompts are deliberately detailed and exceed 1,000 words when the shared context and acceptance discipline are included.
Critical scope and safety boundaries
All bank customers, accounts, and transactions are synthetic. The project is a simulator, not a real bank.
All continuously updating exchange activity is simulated unless an authorised and licensed market feed is explicitly configured.
Model 1 predicts short-horizon equity momentum. Model 2 estimates execution cost/liquidity outcomes. These are separate tasks and must not be confused.
Model 2 trained on simulator executions learns simulator mechanics; it is not proof of real-market execution performance.
The LRO combines deterministic cash/ledger calculations with market valuation and model-based estimates. ML outputs are advisory; human approval is required and autonomous real-money trading is prohibited.
LCR/NSFR-style values are educational estimates unless independently validated against current applicable rules by qualified experts.

PROMPT 01 — ANTIGRAVITY 1 — Shared design system and application shell
Tool: ANTIGRAVITY
Copy the complete prompt below into the named tool:
Project Context And Non-Negotiable Requirements
You are contributing to a three-application educational/research ecosystem called Liquidity Risk Optimizer (LRO). The three separately navigable desktop applications are: (A) Bank Simulator, which models four fictional Indian banks and their customers, accounts, deposits, loans, securities, treasury activity and banking transactions; (B) Exchange Simulator, which models a broad Indian-market-inspired exchange with instruments, quotes, order books, trades and market regimes; and (C) Liquidity Risk Optimizer, which consumes bank and exchange events, calculates liquidity and risk metrics, and presents decision-support recommendations. They run on one Windows or Fedora Linux laptop during development, but the architecture should be portable and clearly separable for later deployment.
Technology baseline: Java 25 for desktop/backend services; JavaFX and FXML for the desktop interfaces; PostgreSQL for persistent storage; STOMP messaging through a locally runnable broker for inter-application events; Maven for a consistent multi-module build unless the existing repository has already established a working Gradle convention. Use documented, maintained libraries with compatible versions. Keep the UI, domain logic, database access, messaging, and model-serving adapters separated. Use JavaFX Task/Service or dedicated executors for background work; never block the JavaFX application thread. Use migrations (Flyway or an equivalent established tool), environment-based configuration, structured logs, and automated tests.
This is a SIMULATOR, not a real bank, brokerage, licensed exchange, or production trading system. All generated customers, accounts, transactions, bank profiles, orders and fills must be fictional and clearly labelled synthetic/demo. Never imply affiliation with Axis Bank or any real institution. Do not scrape or redistribute licensed market data. Historical data imports must respect provider licences and terms. The exchange must clearly label generated/replayed prices as simulated; do not claim it is a live connection to NSE/BSE unless an authorised, licensed feed is actually configured. The phrase “live” in this project means continuously updating simulated activity and events.
Create four separate PostgreSQL schemas with the same normalized table design but different seed populations: a large healthy bank (target at least 10,000 customers), a medium bank (at least 7,500 customers), a small healthy bank (at least 5,000 customers), and a distressed bank (at least 5,000 or a justified proportionate count, with higher synthetic NPA share and lower deposits relative to assets). Assign profiles through explicit seed-generation configuration, not hard-coded assumptions in UI code. Scale other entities realistically: multiple accounts per customer, loans, deposits, repayment schedules, collateral, branches, employees/roles, transactions, ledger entries, holdings, government securities, Treasury bills, corporate debt, equity positions, cash, encumbrances, counterparties, maturity ladders, stress results and audit records. The large-bank seed should include at least 1,000 loans and around 500 G-Sec holding/lot records as a starting target; scale other bank populations proportionately. Use synthetic identifiers, plausible distributions, referential integrity and deterministic random seeds so tests are reproducible.
The exchange catalogue should cover the relevant instrument families rather than pretending every family has exactly 1,000 real securities: equities, indices, ETFs, mutual-fund-like units where suitable, government securities, Treasury bills, corporate bonds, money-market instruments, listed futures and options, FX pairs, gold and other commodities, and eligible simulated cash/short-term instruments. Use configurable seed targets (for example, up to 1,000 synthetic equity instruments and large synthetic records for other categories). Do not invent real ISINs or imply fictional instruments are genuinely listed. Store instrument category, issuer, currency, tick/lot rules, maturity/expiry, contract multiplier, trading calendar and source/provenance.
The two ML models only are in scope: Model 1 predicts short-horizon equity market momentum from historical OHLCV and market features; Model 2 estimates liquidity/execution outcomes such as slippage, execution cost, achievable proceeds or probability of completing a proposed sale from order-book, quote, volume and simulated execution data. Use Google Colab for model development, training and evaluation. Candidate historical sources include NSE official historical/EOD market reports (access and redistribution subject to terms), Yahoo Finance/yfinance only where its terms and availability permit, and public research datasets such as the UCI Online Retail dataset only if genuinely relevant (it is not a substitute for market data). For Indian equities, prefer licensed/official NSE data or another authorised provider; for rates/G-Secs and macro context use RBI Database on Indian Economy and official RBI/FBIL/CCIL or exchange resources where available and permitted. Clearly document source, download date, licensing constraints, fields, adjustments, missing data and survivorship bias. Model 2 training labels may be generated by the project’s own order-matching simulator, but the report must state that a model trained on synthetic execution labels learns the simulator’s mechanics and is not validated real-world execution evidence.
The optimizer must keep deterministic calculations separate from ML forecasts. Cash and verified ledger balances are calculated directly. Other liquidity calculations must identify assumptions and apply asset-specific treatment; market-sensitive holdings can use executable quotes, valuation models, transparent haircuts and stress scenarios. Show LCR/NSFR-style indicators only as educational estimates, with configurable rules and a warning that regulatory reporting requires expert review and current applicable RBI/Basel rules. Use risk measures where implemented with documented definitions and limits. ML outputs are decision support, not instructions to trade. No autonomous real-money trading. Every proposed action must show forecast horizon, model version, confidence/uncertainty where available, costs, source timestamp, data freshness and a human approval step.
Messaging requirements: define versioned JSON event envelopes with eventId, eventType, schemaVersion, occurredAt, producer, correlationId, entity identifiers and payload. Use clear STOMP destinations for market ticks/quotes, trades, market regime changes, bank transactions, holdings changes, liquidity snapshots, risk alerts and model predictions. Implement reconnect, subscription restoration, duplicate detection/idempotency, bounded queues/backpressure, dead-letter or error handling, heartbeat/health checks, message validation and observability. Persist critical business events before or transactionally with publication using an outbox pattern where practical. Do not publish customer PII on general topics; use synthetic data and minimum necessary identifiers.
Security and quality requirements: use least-privilege database users, parameterized SQL, validation, safe password hashing if authentication is implemented, no secrets committed to source control, role-based permissions, append-only audit events for sensitive operations, transaction boundaries and a double-entry ledger for money movements. Use BigDecimal for money and explicit currency/rounding rules; use Instant/OffsetDateTime and a defined timezone strategy. Add unit, integration, migration, end-to-end, negative-path and performance tests. Provide useful error messages, accessible keyboard navigation, labels and tooltips that explain financial terminology in plain language. Package for Windows and Fedora Linux with documented prerequisites and reproducible commands. Do not claim completion until the feature compiles, tests pass and a reproducible manual verification path is documented.
Task-Specific Instructions
Build ONLY the frontend presentation layer and reusable JavaFX/FXML UI shell for the three applications. Do not implement database access, STOMP connectivity, market logic, financial calculations, or model inference in this prompt. First inspect the existing repository and preserve any working conventions. Create a shared visual design system with consistent typography, spacing, table density, chart framing, navigation patterns, empty/loading/error states, status chips, confirmation dialogs, and plain-language help. Make the three applications visually related but unmistakably distinguishable by name and accent treatment: Bank Simulator, Exchange Simulator, and Liquidity Risk Optimizer.
Design for desktop use at common 1366×768 and 1920×1080 resolutions, while allowing resizing and sensible minimum window sizes. Use FXML and controllers or the established JavaFX pattern already in the repository. Keep controller code limited to presentation state and navigation; use mock view-model data only, isolated behind interfaces that later backend prompts can replace. Do not invent backend endpoints. Include a consistent left navigation rail, top bar with application name, connection/status indicator placeholders, current simulation clock placeholder, user/profile menu placeholder, and contextual help. Include keyboard focus states, accessible labels, tooltips, readable contrast, and responsive table columns. Create reusable components for KPI cards, data tables, filter bars, date/time range pickers, empty states, confirmation dialogs, notification banners, charts, and detail drawers.
Use finance-friendly visual language without relying only on colour: every warning must include text/icon/label. Use labels understandable to a person without advanced finance knowledge, with the technical term in a tooltip or expandable “What does this mean?” panel. Build a mock navigation flow that can be clicked through end-to-end, and include sample synthetic/demo badges wherever fake data is shown. Include a frontend README describing FXML/view locations, navigation structure, mock-data boundaries and how to run the UI. Keep this prompt strictly frontend-only; later prompts will connect services and data. Deliver a concise inventory of files changed, run instructions, and screenshots or a manual verification checklist if the environment supports them.
Implementation Discipline And Acceptance Format
Work incrementally. Inspect existing files first, preserve unrelated work, and make changes only for this prompt’s scope. If a dependency, source dataset, broker feature or OS capability is unavailable, do not fabricate success: document the blocker, implement a clean interface or deterministic local fallback where safe, and provide the exact follow-up action. Never place passwords, API keys, licensed datasets or personal data in source control. Use synthetic fixtures for tests and label them.
Before finishing, run the narrowest relevant formatter/build/tests and then the broader available test suite. Report: (1) files created/modified; (2) architecture and key decisions; (3) commands actually run; (4) test results with counts and failures; (5) manual verification steps; (6) known limitations and next prompt dependencies. Keep all monetary arithmetic precise, all date/time handling explicit, all data sources traceable and all recommendations explainable. Use parameterized SQL, transactions and migrations. Add automated tests for success, invalid input, failure, duplicate delivery and stale data where relevant. Do not leave TODO placeholders for core behaviour requested in this prompt; if something cannot be completed, state it plainly and create a tracked limitation.
Cross-platform requirements apply throughout: avoid OS-specific hard-coded paths, document shell differences, externalize configuration, and verify packaging commands. The final system must be easy to navigate for a user without deep finance expertise, but technical details should remain available in drill-down views and documentation. Do not label generated activity “real market data.” Do not describe model predictions as certainty, do not present illustrative LCR/NSFR values as official regulatory reports, and do not enable autonomous real-money trading.
